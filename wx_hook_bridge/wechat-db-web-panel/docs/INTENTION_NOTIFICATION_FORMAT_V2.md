# 意向单通报格式 V2

## 设计目标

现有通报强调“谁刚出了一单”，但管理者无法立即判断：

- 小组目前整体完成多少，和昨日同期相比是变好还是变差。
- 全组有多少人已经破零，还有谁仍是零单。
- 本次新增后，当事人的单量、名次和破零状态发生了什么变化。
- 组内成员当前集中在哪个档位，而不是只看某一个人。

V2 采用两层通报：高频消息保持短，阶段节点再展开完整名单。

## 推荐发送规则

| 通报 | 触发时机 | 目的 |
| --- | --- | --- |
| 每单快报 | 每产生 1 张新意向单 | 立即知道谁有变化，以及小组破零进度 |
| 阶段战报 | 每个小组累计到 5、10、15、20 单；12:00、16:00、18:30 仅 4 个购机组各一条 | 查看完整组内分布和待破零名单 |
| 今日收官 | 每日 21:00 仅 4 个购机组各一条 | 复盘小组结果，明确次日关注对象 |

定时阶段战报和收官战报仅通报呼叫中心一组、二组、四组和润汇外呼小组，对应上游外呼组 ID 为 `2`、`3`、`4`、`5`；呼叫中心三组不属于购机组，不在通报范围内。其他小组不生成定时消息，历史队列中的其他小组也不再补发。每单快报、每累计 5 单触发的阶段战报和“全场累计”统计口径不变。

不建议每张新单都展开所有成员。完整名单反复发送会刷屏，真正的变化反而不容易被看见。

## 格式一：每单快报

适合每一张新单，控制在手机一屏内。

```text
【新单｜呼叫中心四组】
王静 +1｜个人 2 单
18:17 录单

小组 15 单｜昨日同期 12 单
已破零 8/10 人｜待破零 2 人

本次变化：1→2，并列第 1
全场累计 48 单
```

若这是当事人的第一单，将“本次变化”替换成更醒目的状态：

```text
本次变化：0→1，完成破零
小组破零率：70%→80%
```

## 格式二：阶段战报

推荐作为主要的完整通报格式。按单量分档比逐人排行榜更短，也能直接看出组内结构。

```text
【阶段战报｜18:30】
呼叫中心四组

今日 15 单｜昨日同期 12 单｜+25%
已破零 8/10 人｜破零率 80%

【组内分布】
2 单：王静、李敏、陈芳、赵宁
      周倩、刘欣、吴悦
1 单：孙晴
0 单：杨帆、何佳

【本阶段变化】
周倩 0→2｜新破零
王静 1→2｜升至并列第 1
孙晴 0→1｜新破零

待破零：杨帆、何佳
全场累计 48 单
```

阶段变化的比较基准为“上一次阶段战报”，昨日同期只用于小组总量比较，避免两个口径混在一起。

## 格式三：今日收官

用于当天最后一次复盘，弱化单次喜报，突出完成面和第二天动作。

```text
【今日收官｜呼叫中心四组】

今日 21 单｜昨日 17 单｜+4 单
已破零 9/10 人｜破零率 90%
人均 2.1 单｜最高 4 单

【成员结果】
4 单：王静
3 单：李敏、陈芳
2 单：赵宁、周倩、刘欣
1 单：吴悦、孙晴、杨帆
0 单：何佳

今日新破零：周倩、孙晴、杨帆
连续两日增长：王静、刘欣
明日优先关注：何佳
```

## 字段口径

| 字段 | 计算规则 |
| --- | --- |
| 今日单量 | 按意向单业务日期统计，不按消息发送时间统计 |
| 昨日同期 | 昨日从 00:00 到当前通报时刻的累计单量 |
| 在岗组员 | 当天已拨打不同号码数量大于 10 的组员；恰好 10 个不计入 |
| 已破零 | 今日单量大于 0 的在岗组员数 |
| 破零率 | 已破零人数 / 当日在岗组员总数 |
| 待破零 | 在岗且今日单量等于 0 的完整名单 |
| 本次变化 | 本张单落库前后，当事人的单量、名次和破零状态变化 |
| 本阶段变化 | 当前阶段战报与该组上一份阶段战报的差值 |
| 连续增长 | 至少连续两个完整工作日高于前一日，不使用未结束的当天判断 |

并列名次使用竞赛排名，例如 `1、1、3`。名单过长时按每行最多 4 人换行，不截断零单人员。

## 数据要求

上游事件生产端与机器人现已共同支持 `data.team_snapshot`。历史事件不会重算快照；从首张携带 `complete: true` 的实时新单开始，机器人会可靠计算在岗、破零率和零单名单。

上游事件或独立汇总接口需要补充以下快照，才能上线完整 V2：

```json
{
  "team_snapshot": {
    "complete": true,
    "group_id": 4,
    "group_name": "呼叫中心四组",
    "snapshot_at": "2026-09-04T18:17:00+08:00",
    "group_today": 15,
    "group_yesterday_same_time": 12,
    "overall_today": 48,
    "members": [
      {
        "user_id": 101,
        "name": "王静",
        "dialed_number_count": 26,
        "intention_today": 2
      },
      {
        "user_id": 102,
        "name": "何佳",
        "dialed_number_count": 18,
        "intention_today": 0
      }
    ]
  }
}
```

`dialed_number_count` 必须是当天已拨打的不同电话号码数量，不是重复呼叫次数。机器人只信任 `complete: true`、日期与本单业务日期一致、成员字段完整的快照。

在完整花名册不可用时，系统降级为“今日已有 8 人出单”，不显示 `8/10`、破零率或零单名单，避免把未知人员误报为零单。页面分别显示“等待今日首单”“已接入”或“安全降级”，便于判断真实接入状态。

## 推荐结论

默认启用“每单快报 + 阶段战报 + 今日收官”。这样既保留即时激励，也能持续看清组内完成面、零单人员和变化趋势。

定时战报使用机器人专用实时快照接口。每个时点提供 30 分钟故障恢复窗口；仅将 4 个购机组的可用快照拆成独立消息并先写入本地 SQLite，再按组名排序、间隔约 2.5 秒发送。购机组缺失或快照不完整时会在窗口内重试，其他小组的数据缺失不影响该时点完成。幂等键由日期、时点、外呼组和目标微信群共同确定，单组或单群失败不会导致其他组重复发送。
