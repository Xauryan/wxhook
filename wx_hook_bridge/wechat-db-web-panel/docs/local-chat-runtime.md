# 本地聊天服务启动与恢复

网页入口为 http://127.0.0.1:5173/chats。微信桥接默认监听 19088，聊天 API 默认监听 8765。

在正常 Windows PowerShell 中运行项目根目录的启动脚本：

~~~powershell
powershell -NoProfile -ExecutionPolicy Bypass -File "G:\project\code\jqr\restart-chat-service.ps1"
~~~

脚本先核验监听端口及运行进程的项目 Python 路径、模块、端口，处理已失去监听的同项目旧后端，然后启动受控 API。其他项目进程、微信、桥接和前端不在停止范围。进程信息查询失败时立即停止脚本，不把拒绝访问当成没有进程。

API 由 backend.service_runner 启动，保留调用者原有权限。GET /api/runtime/health 只提供本机运行状态和本次工作进程标识，独立于 SQLite 和微信。连续健康检查失败或工作进程退出时，管理器仅结束自己启动的进程树并重启 API；连续启动失败有上限，日志位于脚本输出的目录。业务请求不会被重放。

前端由 `backend.web_service_runner` 独立守护，提供已有 `frontend-next/dist` 构建，不在启动时下载依赖或重新编译。Windows 使用同一用户的 WMI 进程创建接口启动隐藏的管理器，不依赖临时命令或验收会话存活，不提权，也不注册开机任务。前端退出或连续三次健康检查失败后，只回收并恢复该管理器拥有的前端进程；连续五次恢复仍无法稳定启动时停止恢复并记录失败，避免无限重启。正常运行 30 秒后清零连续失败次数。前端不会重放聊天请求，也不会重启 API、微信或桥接。

前端的独占进程锁、状态和日志在 `.cache/runtime/web-5173/`：`state.json` 提供管理器及工作进程 PID、创建时间、实例、状态、恢复次数和最近退出码；`events.jsonl` 记录状态变化，`web.err.log`、`runner.err.log` 保留错误。`GET /__jqr_web_health` 标识当前工作进程。重启脚本现在会校验该实例、端口所有者、`/chats` 页面 HTML，以及经前端代理读取的 API 实例；全部通过后才输出 Web 地址和成功结果。重复启动会复用已核验的管理器，发现不属于项目的端口占用时拒绝操作。

只需恢复前端、保留当前 API 时运行：

~~~powershell
powershell -NoProfile -ExecutionPolicy Bypass -File "G:\project\code\jqr\wx_hook_bridge\wechat-db-web-panel\scripts\start-web.ps1"
~~~

此方式常驻于当前 Windows 用户会话；退出 Windows 或重启电脑后需重新运行启动脚本。恢复机制测试会结束独立测试前端并核对新 PID、实例及 HTTP 返回，不会发送微信消息。

每次发送仍强制验证当前桥接进程、真实打开的 contact.db 和账号一致性。Windows 如果拒绝源进程句柄访问，通讯录和发送保持关闭；不会降级使用旧账号路径、旧解密快照或未经核验的联系人。

页面分别显示本地服务未连接、正在读取账号、微信未连接和接收链路未就绪。本地 API 不可用时不显示虚构的零积压、零丢弃，也不要求已经登录的用户重新登录。

本地测试使用独立 HTTP 子进程模拟监听丢失，验证原进程仍存活时能够结束自有进程树并恢复新工作进程。这是运行机制验证，不能替代真实微信账号、收发消息和浏览器验收。

近期聊天消息有独立的回读任务，不等待完整历史归档导入。任务从经过当前账号与微信进程核验的消息库快照读取最近活跃会话的尾部，包含本人从网页、手机或电脑微信发出的消息；只使用真实源记录，不把发送请求回执当作已送达消息。重复快照不会产生重复消息或无意义的消息增量，旧归档快照也不能覆盖较新的近期正文。

`GET /api/chat/status` 的 `recent_syncing`、`recent_updated_at`、`recent_error` 用于观察近期回读；`history_syncing` 仍表示完整归档任务。近期任务每轮完成后至少间隔 5 秒，实际回显还取决于源库快照读取耗时。每轮优先读取最近 24 小时内最活跃的 80 个会话、各消息分片中每会话最新 60 条记录；完整归档仍在后台继续。

聊天数据库快照按账号和分片保留最新两个版本。后台导入、近期回读和发送回读通过进程租约保护正在读取的快照；已发布历史清单引用的数据库也保留，用于语音等资源读取。读取完成后释放租约并淘汰旧版本，进程退出后的残留租约在下轮回收。快照发布与清理使用跨进程锁，清单无法读取时跳过清理。只清理 `.cache/chat_sources` 下符合快照命名规则的文件，不修改微信原始数据库。

可用项目 Python 环境运行 `python -m backend.app.snapshot_cache --cache-root <panel>/.cache` 查看可回收文件，加 `--apply` 执行同样带引用保护的清理。恢复旧版本服务时，应先停止旧快照读取进程，再执行首次清理，避免旧进程未登记租约。

网页发送文本后会立即显示独立的本地发送预览，并标注“正在发送”“已提交，等待微信回显”“结果未确认”或“发送失败”。预览按账号、会话及请求 ID 隔离，保存在当前浏览器标签页会话中；不写入真实消息缓存或计入消息总数。微信回读的新消息到达后，预览按一对一关系撤下，真实消息始终保留原有消息 ID，重复文本不会合并真实记录。失败和未知结果不会自动重发。本地预览同步更新，不依赖浏览器后台标签页可能延迟的定时器通知。

发送提示跟随对应请求的真实回显：当前会话收到已匹配的微信原生消息后，同时收起本地等待气泡和输入框下方的受理提示，无需切换会话。回显先于 HTTP 受理响应到达时，后到的受理响应也不再恢复提示；较早请求的回显不影响后续请求的提示，失败和结果未知的提醒保留。

附件恢复：缺少资源时显示“暂未找到本地图片/文件”等准确状态；可见附件最多每 15 秒重查三次，回到页面时重查未找到的资源。点击重新检查会带 refresh=true，后台针对单条消息读取当前账号快照中的附件映射，并在对应聊天目录查找后续下载的文件；元数据查询、扫描时间和条目数有上限，不重新导入整份聊天历史。当前快照尚无映射时继续等待后台同步，不跨聊天猜测文件，也不自动联网下载。
